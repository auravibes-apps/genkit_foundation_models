# Apple Foundation Models Usage For Text And Tools

Checked against Apple Foundation Models docs on 2026-05-28.

Apple's `FoundationModels` framework exposes the on-device model that powers Apple Intelligence. This package should keep all direct framework usage in Swift, behind a Pigeon-generated Host API.

## Target native API concepts

Core concepts to map:

- `LanguageModelSession`: primary interface for generation and streaming.
- Prompt/instruction text: input sent to a session.
- `streamResponse(...)`: async sequence interface for incremental output.
- `Generable`: protocol used for guided structured generation.
- `@Generable`: macro that lets Swift types be generated by the model.
- `@Guide`: macro/annotation for field descriptions and constraints.
- `Tool`: protocol for model-callable native capabilities.
- Tool `Arguments`: usually a nested `@Generable` type describing tool input.
- Tool `call(arguments:)`: async function invoked when the model calls a tool.

## Text generation

Minimal native text flow:

```swift
import FoundationModels

final class FoundationModelsHostApiImpl: FoundationModelsHostApi {
    private let session = LanguageModelSession()

    func generateText(request: NativeGenerateRequest) async throws -> NativeGenerateResponse {
        let response = try await session.respond(to: request.prompt)

        return NativeGenerateResponse(
            text: String(describing: response),
            toolRequests: [],
            finishReason: "stop"
        )
    }
}
```

The exact response text extraction should be confirmed while implementing against the installed SDK because Apple docs are JavaScript-rendered and API details may shift between beta SDKs.

## Streaming text

Streaming uses `streamResponse(...)` and an async sequence:

```swift
import FoundationModels

let session = LanguageModelSession()

for try await partial in session.streamResponse(to: "Write a haiku about Cupertino.") {
    // Convert partial content into a Pigeon event or chunk DTO.
}
```

For Flutter, streaming should not be modeled as one long blocking HostApi call. Prefer one of these designs:

- Pigeon `@EventChannelApi` if the package version and platform targets support Swift event-channel generation.
- Start/cancel HostApi methods plus an event stream for chunks.
- Non-streaming first, then add streaming after text and tool calls are stable.

## Structured output

Apple supports guided generation into Swift types conforming to `Generable`:

```swift
import FoundationModels

@Generable
struct Customer {
    let name: String
    let coffeeOrder: String
    let visualDescription: String
}

let session = LanguageModelSession()
let customer = try await session.respond(
    to: "Generate a unique coffee shop customer.",
    generating: Customer.self
)
```

For the Genkit provider, do not expose structured output until there is a clear schema bridge. Dart/Genkit schemas do not automatically become Swift `@Generable` types at runtime. Initial provider scope should be text plus tool requests.

## Native tool definition

Apple tool usage conforms to `Tool`. Apple's documented example shape:

```swift
import Contacts
import FoundationModels

struct FindContacts: Tool {
    let name = "findContacts"
    let description = "Find a specific number of contacts"

    @Generable
    struct Arguments {
        @Guide(description: "The number of contacts to get", .range(1...10))
        let count: Int
    }

    func call(arguments: Arguments) async throws -> [String] {
        var contacts: [CNContact] = []
        // Fetch contacts using the arguments.
        return contacts.map { "\($0.givenName) \($0.familyName)" }
    }
}
```

## Tool strategy for Genkit

There are two viable strategies.

Preferred first strategy: Dart-owned tools.

- Genkit already owns tool declarations and execution.
- Swift receives tool schema summaries and makes them available to the model.
- When the model asks for a tool, Swift returns a tool request DTO to Dart.
- Genkit executes the Dart tool.
- Dart sends a tool response back through the next model request.

Alternative strategy: Swift-owned tools.

- Swift implements concrete `Tool` conformers.
- The native model invokes Swift tools directly.
- Dart receives only final text and maybe trace events.
- This is useful for Apple-only capabilities such as Contacts, Calendar, local files, or app intents, but it bypasses Genkit's tool registry.

Use Dart-owned tools for the provider MVP. Add Swift-owned tools later as explicit native extensions.

## Mapping Genkit tool declarations to Apple tools

The hard part is that Swift `Tool.Arguments` is statically typed and commonly generated with `@Generable`. Genkit tool schemas are dynamic at runtime.

Implementation options:

- Support a generic Swift tool adapter with JSON-like arguments if the Foundation Models SDK allows a dynamic argument type.
- Generate Swift tool wrappers at build time for known tools.
- Keep native tools static and expose only a limited set from the plugin.
- For MVP, return unsupported for arbitrary Genkit tools until a dynamic adapter is proven.

## Availability gates

Swift should check runtime availability before generation:

- OS version supports `FoundationModels`.
- Device supports Apple Intelligence and the system language model.
- Model is available/enabled for the current user and language.

Return a structured unavailable error instead of letting a native exception leak across the platform channel.

## Data sent across Pigeon

Use simple DTOs:

- `NativeGenerateRequest`: messages, system instruction, config, tool declarations.
- `NativeMessage`: role, parts.
- `NativePart`: text, tool request, tool response, unsupported type marker.
- `NativeToolDeclaration`: name, description, JSON schema string/map.
- `NativeToolRequest`: id, name, JSON arguments.
- `NativeToolResponse`: id, name, JSON output or error.
- `NativeGenerateResponse`: text, parts, tool requests, finish reason, raw debug metadata if needed.

Keep DTOs JSON-like because Pigeon uses Flutter's standard message codec and maps cleanly between Dart and Swift.
